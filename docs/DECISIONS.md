## ADR-001：上游保持薄，RBatis-Plus 承载缓存产品能力

**状态**：已接受

### 上下文

生产级缓存需要可靠的执行上下文、通用拦截钩子和事务生命周期事件。这些能力对 trace、metrics、tenant、audit 等插件同样有用；缓存 SPI、后端和策略则属于 RBatis-Plus 的产品能力。如果把完整缓存实现放入上游 `rbatis`，会扩大上游 API、依赖和维护范围。

### 决策

上游 `rbatis` 只提供通用、缓存无关的扩展基础，包括执行上下文、操作类型、稳定的 before/after/error（或 around）钩子，以及事务 begin/commit-success/rollback 事件。RBatis-Plus 提供 `CacheStore` SPI、`CacheIntercept`、缓存策略、Key/Envelope 协议、内存与 Redis 后端、宏元数据和可观测能力。

### 备选方案

1. 把缓存 SPI、拦截器和后端全部放入上游 `rbatis`。
2. 不改上游，仅在 RBatis-Plus 中通过 `task_id`、执行器名称和 SQL 猜测上下文。
3. 在 CRUD 宏中分别实现缓存，不建设统一执行层能力。

### 后果

- 上游 API 保持通用且依赖较少。
- RBatis-Plus 可以独立迭代缓存产品能力。
- 生产级事务语义依赖上游接受少量通用增强；在此之前只能提供有明确限制的兼容模式。
- 两个项目需要维护事件与上下文的兼容矩阵。

### 反转条件

当上游明确决定将二级缓存作为内建产品能力，愿意承担缓存 SPI、后端生态和兼容性维护，或通用钩子无法满足缓存正确性时，重新评估边界。

## ADR-002：缓存原始 `rbs::Value`

**状态**：已接受

### 上下文

拦截器在泛型解码前接触数据库返回的 `rbs::Value`。最终返回类型 `T` 因调用方而异，缓存 `T` 会引入类型擦除、重复入口或按类型分裂的 Key。

### 决策

缓存持有的对象是 owned `rbs::Value`；命中后把 `Value` 放回统一查询路径，并继续使用既有 `decode<T>`。分布式后端通过带版本的 Envelope 序列化该值。

### 备选方案

1. 缓存最终泛型类型 `T`。
2. 缓存数据库驱动的行或结果集对象。
3. 缓存 JSON 文本并在命中后直接反序列化为 `T`。

### 后果

- 所有查询返回类型共享同一缓存入口。
- 无需存储 `Any`，也不绑定具体数据库驱动结果类型。
- 内存后端需要克隆或共享 owned `Value`。
- `rbs::Value` 或编码格式升级时必须通过版本协议处理兼容性。

### 反转条件

当 `rbs::Value` 无法稳定表示所需结果、序列化成本被基准证明不可接受，或 RBatis 提供更稳定的驱动无关结果协议时，重新选择缓存对象。

## ADR-003：显式标签优先于完整 SQL 解析

**状态**：已接受

### 上下文

精确失效需要知道查询和写操作依赖的数据。完整 SQL 解析必须处理多方言、CTE、子查询、JOIN、动态 SQL、触发器和存储过程，仍不能可靠覆盖间接写入。

### 决策

查询与写操作通过宏元数据或运行时策略显式声明 namespace 和 tags。未声明精确依赖时，使用保守的 namespace 失效。首个生产版本不以完整 SQL 解析作为正确性前提。

### 备选方案

1. 对所有 SQL 进行完整语法解析并自动推导表依赖。
2. 用正则或 SQL 前缀提取表名。
3. 所有 DML 都清空全部缓存。

### 后果

- 失效语义可预测、跨方言且可测试。
- 用户或宏生成器需要维护标签元数据。
- 标签遗漏可能产生陈旧缓存，因此默认回退必须保守。
- 后续可增加 SQL 分析作为辅助建议或校验，但不能替代显式契约。

### 反转条件

当存在覆盖目标方言和动态 SQL 的成熟解析器，并能以测试证明自动依赖推导比显式标签更可靠且维护成本更低时，重新评估默认策略。

## ADR-004：事务内默认绕过二级缓存

**状态**：已接受

### 上下文

事务查询可能需要读取未提交写入、锁定行或满足隔离级别语义。共享二级缓存不能表达连接内的事务可见性，错误命中会破坏读己之写和锁语义。

### 决策

事务内查询默认既不读取也不回填共享 L2 缓存。锁定查询和显式 bypass 查询始终绕过缓存。未来即使允许事务缓存，也必须通过显式策略启用并定义隔离语义。

### 备选方案

1. 事务内正常读写共享缓存。
2. 事务内读取共享缓存但不回填。
3. 为每个事务维护私有缓存。

### 后果

- 默认行为优先保证事务正确性。
- 事务密集型负载的命中率下降。
- 实现无需推断事务快照和隔离级别。
- 必须依赖显式 `ExecutorKind` 或事务上下文，不能使用执行器名称猜测。

### 反转条件

当上游提供稳定的事务快照标识，并且私有事务缓存或隔离感知缓存通过一致性测试时，可以为特定场景增加显式 opt-in 模式。

## ADR-005：仅在提交成功后执行事务失效

**状态**：已接受

### 上下文

事务中的 DML 在提交前对其他事务不可见，并且可能回滚。立即失效不会暴露未提交数据，但会造成无效抖动，也无法表达提交成功这一真实变更点。

### 决策

事务 DML 只把待失效 tags/namespace 合并到 `tx_id` 对应的 pending 集合。仅在 commit-success 事件后执行失效；rollback 时丢弃集合；commit 失败时不执行成功路径。非事务 DML 仍在数据库执行成功后失效。

### 备选方案

1. 事务 DML 成功后立即失效。
2. 在事务开始或写入前失效。
3. 无论 commit 或 rollback 都失效。

### 后果

- 失效与数据库可见性边界一致。
- 需要上游提供可靠的 commit-success/rollback 生命周期事件。
- 进程异常可能遗留未执行的本地 pending 状态，外部写入仍需短 TTL、CDC 或主动失效等补充机制。
- 同一事务的重复标签可以合并，减少后端操作。

### 反转条件

当底层数据库或事件总线提供更可靠的提交日志/CDC 失效机制，或无法获得 commit-success 事件时，改用该机制；降级方案必须明确标注一致性限制。

## ADR-006：使用版本化标签实现 O(1) 失效

**状态**：已接受

### 上下文

维护 `tag -> keys` 反向索引需要处理 TTL、淘汰和并发更新产生的陈旧索引；Redis 中按标签扫描 Key 成本高且阻塞风险大。

### 决策

每个 tag 维护单调递增的版本。构建查询 Key 时包含相关 tag 的当前版本；失效时递增版本，而不是扫描和删除所有关联 Key。旧 Key 由 TTL 和容量淘汰自然回收。

### 备选方案

1. 维护精确的 `tag -> keys` 反向索引并逐个删除。
2. Redis `SCAN` 后按模式删除。
3. 仅使用 namespace 全量清除。

### 后果

- 失效操作为 O(1)，适合内存和多节点 Redis。
- 旧数据会在 TTL 到期前占用空间，因此必须设置 TTL 和容量上限。
- Key 构建需要读取标签版本，并定义并发回填与失效的顺序。
- 版本存储本身需要原子递增和可观测性。

### 反转条件

当后端原生提供低成本、原子且可证明一致的标签失效，或旧 Key 的空间成本超过版本化方案收益时，改用后端原生索引。

## ADR-007：Redis 作为可选 crate 和 feature

**状态**：已接受

### 上下文

Redis 后端会引入客户端、异步运行时 feature、连接管理和编解码依赖。并非所有 RBatis-Plus 用户都使用分布式缓存，将这些依赖放入默认构建会增加编译时间、体积和冲突面。

### 决策

Redis 实现位于独立可选 crate `rbatis-plus-redis`，并通过显式 Cargo feature/依赖启用。核心缓存 SPI 和内存能力不得依赖 Redis；默认构建不启用 Redis。

### 备选方案

1. 将 Redis 客户端直接加入 RBatis-Plus 核心 crate。
2. 只提供 Redis，不提供后端无关 SPI。
3. 让用户在应用内自行实现所有 Redis 适配。

### 后果

- 不使用 Redis 的用户不承担其依赖成本。
- Redis 后端可以独立选择客户端 feature 和发布节奏。
- 工作区需要执行默认特性、Redis 特性以及常见 runtime 组合的 CI。
- 文档必须明确 crate、feature、runtime 和版本兼容关系。

### 反转条件

当 Redis 成为产品不可分割的强制运行时依赖，且独立 crate 造成的版本协调成本显著高于可选依赖收益时，考虑合并。

## ADR-008：缓存故障默认 Fail Open

**状态**：已接受

### 上下文

二级缓存是性能优化，不应默认成为数据库可用性的前置条件。网络、序列化或后端容量故障若直接中断业务，会扩大故障域。

### 决策

`get`、`set` 和一般失效操作失败时默认 Fail Open：记录结构化日志与指标，查询回退数据库，写入主路径继续。允许安全敏感或强一致场景通过显式策略选择 Fail Closed；失效失败必须告警，并由短 TTL、重试或外部失效机制限制陈旧窗口。

### 备选方案

1. 所有缓存错误默认 Fail Closed。
2. 静默忽略缓存错误，不记录指标。
3. 仅读取失败开放，写入或失效失败关闭。

### 后果

- 缓存故障通常不会导致数据库业务直接失败。
- 缓存不可用时数据库负载可能突增，需要熔断、限流和容量预案。
- 失效失败可能延长陈旧数据窗口，因此 TTL 不能无限。
- Fail Open 不能吞掉可观测信号。

### 反转条件

当特定业务证明缓存承担授权、幂等或其他正确性职责，数据库回退反而不安全时，该策略必须按 namespace 显式改为 Fail Closed，而不是改变全局默认。

## ADR-009：Key 与 Value Envelope 均采用版本化协议

**状态**：已接受

### 上下文

Key 包含 SQL、参数类型、数据源及租户/分片上下文；Value 需要编码 `rbs::Value` 和过期信息。编码、哈希算法或数据结构升级时，跨版本进程可能同时访问同一后端。

### 决策

Key 使用明确的 schema version 前缀，并以稳定、类型保真的规范编码生成摘要；不得使用 `Debug` 输出，也不得泄露敏感参数。Value 使用版本化 Envelope，至少记录协议版本、codec、创建/过期时间和 payload。新版本默认写新协议；读取兼容窗口和旧 Key 的 TTL 回收策略须在迁移说明中定义。

### 备选方案

1. 使用无版本的字符串拼接 Key 和裸 payload。
2. 仅给 Key 加版本，Value 直接固定为某一种编码。
3. 原地升级协议并要求一次性清空全部缓存。

### 后果

- 支持滚动升级、编码演进和明确的兼容边界。
- Key/Envelope 协议成为需要测试和发布说明的公共契约。
- 版本升级期间可能短暂降低命中率并增加存储占用。
- 需要 golden vectors 验证跨进程、跨版本编码一致性。

### 反转条件

当缓存后端完全进程私有、生命周期严格短于应用版本且不存在滚动升级时，可在该后端内部简化 Envelope；共享后端不得取消协议版本。
